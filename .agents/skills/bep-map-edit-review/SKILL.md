# BEP scientific map — specific authoring, correction and owner-understanding policy

**This skill governs MEANING and AUTHORIZATION, not Git technique.** Use [`reversible-change-review`](../reversible-change-review/SKILL.md) for checkpoint/diff/remote verification/revert. Read BEP `conventions.md` §13, the [node contract](../../../Academics/BEP/Catalysis/research/notes/bep_mindmap_node_contract_2026_10_20.md), and the actual dataset before a targeted write. The existing viewer is not the sole source of truth.

## A. Decide WHICH map and which operation

**Conceptually different maps, not necessarily already separate implemented files:**

| Destination | Agent can independently author? | Highest knowledge state | What changes mean |
|---|---|---|---|
| AI scientific **reference** map / isolated new research draft | **Yes**; no per-node owner permission needed | Grey **Idea** / yellow **AI worked out** only | AI proposals/interpretations, not owner scientific knowledge |
| Owner's **personal/approved graph** or any `human_worked_out` (blue) status | **NO**, not without exact current owner approval | Blue only after explicit confirmation | Owner-chosen graph change; never implied by AI citation, Git merge or UI click |
| Source claim flagged as **human verified** | **NO** without actual review/evidence by owner | Independent status | Verification of a given citation-to-claim link, not maturity |

**When the user says "change the actual graph":** determine whether the destination is the AI sandbox/reference draft or the personal/canonical presentation/understanding graph. If unclear and the write would touch the user's graph, **propose an exact patch and ask approval**; meanwhile AI may continue separate reference research. A request to "build the AI reference map" authorizes AI-only draft edits, not personal graph promotion. Do not call the legacy `promote_draft_node(..., new_tier=2)` or `/api/promote` as an approval shortcut.

**Approval transaction for the personal graph:**
1. Show **exact node IDs, titles, before/after parent/status/content, and scope** of change. For a single straightforward user-directed change, the user request itself may be explicit approval; no redundant approval dialogue.
2. If the instruction is ambiguous, ask one specific question; never infer approval from silence, the presence of a draft, a previous generic permission, an AI-generated explanation, or a successful Git operation.
3. Apply only the approved delta to the intended dataset/layer, with explicit record of user authorization (where available). Confirm no other personal nodes changed and no citation status was silently promoted.
4. Deliver an inspectable diff and revert instructions through the general workflow.

## B. Map-specific scientific model

- Single BEP scientific root. The owner previously selected first branches Physics / Mathematics / Systems & Control. Broad themes may be reconsidered for AI research. **No maximum depth**; levels 7, 8, 9+ are fine.
- Main subject: the original BEP proposal, dynamic acetylene semi-hydrogenation in a packed-bed reactor, with chemical/transport physics, catalyst coverages, mathematical numerical model, experiments, estimation and control. Broad supporting science is welcome with an explicit connection to this context; do not turn the task into unrelated encyclopedic expansion.
- The A–M research dossiers may inform multiple scientific branches; they are **source provenance/cross-links**, not obligatory siblings of the three science branches or forced tree ancestors. Their order is an **exploration itinerary**, not a fixed taxonomy.
- Preserve stable node IDs, parent ancestry, human decisions, annotations, source locators, open questions and important differences between literature models. Do not equate a speculative mechanism with experimentally validated kinetics; source-specific parameter sets remain conditioned on their catalysts and operating regimes.
- Each AI node is a separate substantive concept with notes/equations/assumptions as warranted. Distinguish (i) idea/unknown, (ii) AI synthesized with attached evidence, (iii) experimentally source-supported claim, (iv) human verified: different epistemic properties, not a ladder inferred from a color.
- **No data loss by serialization:** current Pydantic parser has `extra="ignore"`, so unknown future fields can disappear during *backend* round trips. Do not write unsupported metadata until lossless schema evolution is validated. Display bugs are not source data defects by default. Code and data may advance at different times.
- The present 69-node AI draft is a **historical/provisional precedent**, not an authoritative answer for new independent reconstruction.

## C. Response protocol when the owner objects

A complaint, correction or frustrated reaction is **feedback**, not permission to destroy or replace the whole map:

1. **Restate the precise observed mismatch**, and identify current node IDs and relevant last edit/diff if possible. Distinguish a structural disagreement ("wrong parent"), scientific dispute ("this rate law doesn't apply"), missing information, UI-only presentation, and approval confusion.
2. **No panic reset.** Don't roll back a whole file, regenerate everything, silently "fix" unrelated branches, promote all nodes or commit a guessed interpretation. Preserve the scientific evidence and alternative viewpoints.
3. If clearly wrong **within autonomous AI reference scope**, make the smallest local correction, record the superseded claim as appropriate, run validation and link its patch; no need to ask permission. If owner explicitly requested the personal map correction, apply **only that approved change**. If multiple interpretations remain, **ask one direct, discriminating question** and offer a narrow proposed patch.
4. For requests to undo, inspect commit dependencies and use the reversible-change skill. **Do not delete a historically useful reference draft simply to hide it from a new agent**; use staged exposure and a comparison after an independent freeze, unless deletion is explicitly chosen after trade-off review.
5. Confirm whether the issue was corrected in *data* or only *rendering*. A good-looking graph does not prove correct physical or mathematical claims.

## D. New independent reconstruction mode ("from zero")

When directed to produce an independent AI reference map, **do not seed or imitate the previous dataset**. Treat this as a comparison experiment:

- **Source whitelist during blind stage:** original BEP proposal (`0_Project_Management/main.tex`, relevant proposal `section*.tex`, `references.bib`), and actual primary scientific literature / raw experiment descriptions intentionally selected for the task. Where uncertainty remains, label it rather than borrowing previous map conclusions. The root repository instructions still apply for safety, but skip reading map-specific taxonomy, existing map YAML, old map skill, prior map state/roadmaps and summaries **as scientific inputs** during the blind stage. Read *this authorization protocol* as governance only; do not inherit its example node hierarchy as scientific evidence.
- **No prior-map contamination:** do not open `mindmap/data/bep_draft_overlay.yaml`, prior mind-map taxonomy/specs, C1/C2 generated node contents, old synthesizer's candidate output or earlier AI map examples until the **new independent version is committed and frozen**. The three owner-decided first disciplines may be stated as a known structural constraint; otherwise allow the Level-2 themes/paths to emerge from primary sources.
- Write to a **fresh isolated path** (not the active `bep_map.yaml` or `bep_draft_overlay.yaml`). Include separate source manifest, uncertainty ledger and machine-readable scientific nodes; do not assume the current parser can safely round-trip the new experimental fields. This is a new *dataset*, not a replacement viewer.
- After freezing version 1 at a visible commit SHA, **and only then**, inspect the old map for comparison. Record convergences, surprises, possible bias, missing science and prior errors in a separate comparison artifact. Do NOT silently copy old nodes into the independent baseline.
- This is **instructional blindness**, not a guarantee of information-theoretic isolation: the old map remains in the same Git repository and may appear indirectly in global state/links or search results. Report accidental exposure honestly instead of asserting a perfect blind experiment.

## F. Live map authority, approval bookkeeping and reader discipline

**Owner corrections, 23 October 2026:** Follow the live-map authority and approval-synchronization rules below in addition to the approval transaction above.

- **Authoritative state:** The live `owner_working_map/current_map.yaml` holds current node IDs, ancestry, maturity and scoped approval receipts. State summaries, READMEs, action queues, bridge crosswalks, dated snapshots and Markdown reader pages are **valuable maintained supporting artifacts**, but not independent authorities over the live node's tier/maturity. Continue updating their useful context, questions, links, history and relationships as work progresses. Prefer deriving mutable tier/maturity labels dynamically from the live map; don't copy the same live fields into every artifact. Where a maintained summary contains a current-state statement that becomes stale, reconcile or clearly date/supersede it, while preserving meaningful historical snapshots. Reader/UI should derive current tier and maturity from live graph data. For source review, the record-level `human_verified` flags and evidence ledger are authoritative; maturity never substitutes for source verification.
- **When records agree**, simply proceed while maintaining those artifacts for their distinct functions. **When they disagree**, report the concrete conflict, likely freshness/cause and affected records, then resolve only the fields that actually need reconciliation. A stale explanatory page isn't proof of an unauthorized promotion if the live node and explicit owner decision receipt agree. Keep ongoing guides, cross-links, queues and reader pages useful; don't mass-rewrite fixed historical snapshots or duplicate mutable status fields after a minor stage change.
- **Approval synchronization is a required check:** On each owner-authorized structural placement or maturity promotion, update the live node and its scoped authorization/decision receipt; reconcile any maintained approval index (e.g. `dataset.approved_personal_nodes`) that purports to list approved placed nodes. Verify the sets match or explicitly document intentional differences; don't mistake an outdated secondary index for a live scientific approval denial. Prefer deriving such lists from live node statuses/receipts in the reader where possible. GitHub's file-level API commits may not be atomic across files: read back and report partial failures before claiming completion.
- **Reader-page boundary:** Owner-readable Markdown is primarily the informal explanation (or compact AI explanatory passage) ending with its directly relevant Damian/Zoe question. Technical caveats, per-citation validation, approval metadata, and AI annotations belong in hidden `background_files` or reader-collapsed audit sections—not a long block after the owner's final question. Preserve evidence before splitting. Do not treat the presence of literature in background as a human-verified source.
- **Figures:** Display usable linked figures if the viewer supports the asset; rendering format (SVG/PNG/JPEG/other) is an implementation concern, distinct from scientific verification. Do not infer approval from a figure or treat a joke about a “bump map” as a feature requirement.
- **Publishing versus deadline:** Restricted access for a possible public-facing Methanol Catalysis site (password or TU Delft institutional sign-in, with privacy/IP review) remains a future project. The **Damian map export is a deliverable due Friday, 23 October 2026**, not a future horizon. Prioritize preparing a private reviewable export today, showing the whole owner-selected map and clearly distinguishing personally understood/written nodes from AI-only/Idea material; never label unverified literature as human-verified. Do not publish, deploy or send material to Damian without user approval.

## H. Strict preview gate, non-writing references and A/B/C correction (23 October 2026)

**Owner correction overriding any earlier relaxed interpretation:** EVERYTHING placed in the personal map—even an Idea, an equation, an assumption, a background-linked concept, or a suggested parent—must be **shown to the owner as a specific proposed node before placement**. Show exact title, parent and immediate siblings, short default summary and stage, and wait for acceptance unless owner has already specifically directed *that exact node*. An instruction to describe a taxonomy, add it to the queue, or elaborate one subject does **not** authorize filling its adjacent siblings and children. Human understood is always restricted to the precise concept the owner has discussed. Do not classify a complex PDE as Human worked out because the owner recognizes the word 'radial'.

**The owner owns reader prose:** Reserve `index.md` inside node-page directories for **Informal Writing / Formal Writing** only: text the owner actually spoke/wrote and specifically approved as shareable writing. Do not generate polished `index.md` content at Idea, AI worked out or Human worked out stages. A node at those stages has a short personally reviewed `summary` in the map, appropriately scoped `notes`, optional equations *after preview*, and any detailed AI research in `AI_REFERENCE.md` or another descriptive filename referenced under **hidden `background_files`**, not a default reader `index.md`. A stage label cannot manufacture owner-authored text. Preserve research on reclassification; do not delete it. Do not assume GitHub renders TeX in AI source notes; structured equations belong in node records and source references, not an unreviewed owner-facing page.

**Maturity example from a real owner correction:** A = wall value fixes wall only (**Idea**); B = neglect/average radial variation while retaining axial direction (**AI worked out**, awaiting review); C = whole modeled field held at constant T (**Human worked out only for the elementary fixed-temperature meaning**, not for the entire PDE/heat-transfer derivation). The physical classification is independent from mathematical equation-child stages. Current parent placement of A and B below C is provisional for review, **not a scientific claim that a wall condition logically follows from uniform isothermality**.

**Reverting overreach:** If speculative nodes were inserted under supposed prior authorization, preserve their complete record in research/queue with a reference and restore the owner-only personal graph using a targeted CAS edit. Do **not** mass-reset or undo the other worker's commits. Mark previous approval receipts as historical/superseded, and update the active approval index to match remaining placements. Discuss exact next one node with immediate parent/siblings; do not flood the owner with unrelated PDE formulas.

**Concurrency and return protocol:** Check current science branch HEAD, source blob, existing approved nodes and queued topics every time; other agents may be writing simultaneously. Track pending candidate positions in queue/bridges, not `current_map.yaml`. For cold starts read the latest owner review-gate handoff (if present) and current queue, not old 46/57-node banner claims. In chat, show a compact local tree first with real titles and stages, then discuss only a small amount, then let owner choose; Git receipts can be compact up top and the workflow bureaucracy stays in GitHub.

## G. Exact owner-facing preview, tiny nodes, and the five maturity stages (23 October 2026)

**Live-authoring rule:** A personal-map node must not be introduced merely because an agent researched it. Give the owner the proposed direct parent, exact title, short node summary and the scientific information the default reader would show; receive explicit acceptance before placing. If the owner directly authorizes immediate small Idea nodes and is shown their exact text in chat, that suffices for that scope. Their approval of visible wording **does not** authorize unseen detailed AI reference passages, unreviewed assumptions or source-to-claim verification as *owner-authored/understood*. Put deeper AI material in `notes` with clear AI/provenance sections or linked background; default UI must distinguish it from user writing. Preserve receipts of what the owner actually saw.

**Five stages (the existing live dataset already names all five):**
- `idea`: approved topic/position and previewed minimal summary, not a claim that the scientific framework has been worked out. Questions and AI sources may be connected without implying approval of their contents. An Idea can be as small as an equation or one precise physical nuance.
- `ai_worked_out`: sufficiently complete, coherent **source-scoped** AI explanation of the specific topic, including relevant definitions, interpretation, assumptions/equations and known limits, such that the central remaining development step is the owner's scientific interpretation. A bare source link, generic formula, short guess or a large unprocessed bibliography is **not sufficient**. Applicability to the chosen BEP catalyst may remain uncertain if transparently scoped, but research holes in the topic itself must be stated.
- `human_worked_out`: the owner has explained, tested or specifically approved the **bounded concept** in their own terms. Do not promote a broad umbrella because the owner understands one small mechanism; instead make a child Human worked out and leave the wider parent Idea or appropriately scoped.
- `informal_writing`: actual owner-written or specifically owner-approved conversational prose in a linked reader page, legible/showable to Damian; not automatically thesis-ready. Always keep the independent provenance record.
- `formal_writing`: owner-approved prose essentially suitable for a thesis with minor changes; scientific sources/claim checking remains a **separate** requirement before external use, not inferred automatically from writing quality.

**Reference and page semantics:** Every scientific node maintains its own short `summary` and useful `notes`. The optional `reader_file` must be a real resolving path and must match the current stage: Idea = small concept/question; AI worked out = readable AI explanation with detailed evidence available on request; Human worked out = scoped owner interpretation (AI details segregated); Informal Writing = copyable owner narrative; Formal Writing = thesis-oriented writing. Background reference notes, PDF/scientific figures and citations are informative AI supporting material and are **not** proof of human review. Show current tier/maturity from live node data, rather than copying stale stage labels into Markdown. Before delivery, inspect all linked reader/background/figure paths and validate frontend behavior separately. Require proof before claiming render success.

**Tree granularity and mathematics collaboration:** Favor semantic umbrellas when several meaningful small questions clearly share a scientific parent; even a single equation, assumption, limiting case, parameter definition or nuanced distinction can have its own node. No arbitrary lower bound on explanatory length. Represent a physical process in Physics and its mathematical *description* in Mathematics through typed related-node IDs and bridges, not two copies of the same physical explanation. The existing Mathematics → Mathematical Modeling has separate **Surface Kinetic Equations** and **Reactor Model** branches. When another agent works in Reactor Model, add generic equation examples only under the stable Surface Kinetic Equations parent; do not reparent or rewrite Reactor Model, and verify with fresh current map blob SHA immediately before any write. Source branches behind the live map must be merged/reconciled normally; never replace latest `current_map.yaml` with an older isolated branch copy.

**Batch rule:** For directly approved micro-concepts, show short exact summaries in chat before placing; commit a clearly scoped batch when those previews have been shown, preserving every prior node. All merely suggested or undecided subthemes go to the maintained action queue with candidate parent and tentative stage, and must not be silently inserted as approved personal notes.

## I. Reviewed owner notes, evolving research sources, and active-only work (23 October 2026)

**Exploration is not a mandatory promotion ladder:** A personal node can remain an Idea, AI worked out or Human worked out indefinitely, or be retired/reorganized later. The stages describe the current kind of authorship/evidence, **not** a requirement that every branch must advance to thesis writing. Some nodes may simply remain useful as conceptual distinctions.

**Three distinct note audiences, not just two:** (1) **owner discussion/reference notes** reproduce what the owner actually expressed, accepted or paraphrased back in chat, plus their explicit questions and selected equations, as bounded personally reviewed content; this is not automatically Informal Writing. If separately stored, a clearly named `OWNER_DISCUSSION.md` or equivalent reviewed short summary is appropriate, provided its *entire visible content* was previewed or paraphrased with explicit acceptance; never auto-generate or silently polish extra scientific claims. (2) **AI reading/reference notes for the owner** can be clear explanations offered for future study; label them AI-authored and unreviewed until they have actually been shown in chat. They must not appear as the owner's interpretation or shareable writing. (3) **AI internal research/evidence notes** may be arbitrarily extensive and contain source recon, competing hypotheses, literature detail and audit provenance; keep them non-default and scientifically source-scoped. A single node may link to all three independently. An `index.md` remains reserved for explicitly approved Informal/Formal Writing, not every personally reviewed discussion note. Do not invent unsupported parser fields merely to store these distinctions.

**Research-map migration, not permanent authority:** The independent/integrated AI reference graph is a *source and migration aid*, not necessarily an immortal prerequisite of the personal map. As scientific concepts are reviewed, transfer relevant definitions, bounded claims, equations, literature locators and uncertainties into independently maintainable evidence material alongside the personal graph. Keep original AI-reference IDs as optional temporary provenance/backlinks until migration is verified, then retire redundant dependencies only after checking no evidence disappears. The true literature and BEP implementation are authoritative for claims; the AI map is a synthesized guide and must never substitute for primary source verification.

**Active queue ↔ bridges:** The action queue contains only pending decisions/work, in as much scientific and structural detail as necessary, including prospective full nodes. When work is truly implemented, remove its checked task from the **active** queue (Git history and maintained state/history preserve the receipt); do not confuse archived implementation history with outstanding work. An unresolved or partly implemented bridge must map explicitly to at least one **open queue task**. A wholly placed/resolved bridge can remain as provenance/history without reopening a completed task. At each checkpoint reconcile active bridge IDs and task IDs, avoiding duplicated competing node descriptions. Queue status does **not** imply approval to place a node or add reader prose; each candidate still requires exact owner review.

**Independent audit trigger:** When the owner confirms a parallel science session is finished, a separate agent may inspect and report structural/maturity/evidence/merge concerns. This does NOT authorize unilateral reparenting, rewriting the other agent's scientific nodes, reintroducing withdrawn proposals or issuing human source-verification. Continue the actual owner-approved tree in small parent-and-neighbor snippets.

**This is an authoring protocol. Git diffs are handled by the general reusable skill, not the reason this skill exists.**
